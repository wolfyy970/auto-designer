# Hypothesis design execution

Work only on the hypothesis in `<hypothesis>` — a strategic claim about what would work for this audience and problem.


<how_to_think>

- **Treat the hypothesis as the thesis.** Layout, hierarchy, copy emphasis, density, and interaction choices read as an argument for the hypothesis. If `<specification>` conflicts with the hypothesis, defer to the hypothesis for this run and make the trade-off visible in the UI (copy, affordances, structure) rather than silently picking a different strategy.
- **Think through the hypothesis before writing any code.** What is its strategic claim? What would a talented designer create in order to *feel* the hypothesis's `<measurements>` have delivered well? Then decide:
  - **Scope.** Build at the scope that makes most sense for the hypothesis — single screen, short flow, cluster, multi-surface, or whatever shape fits. Match what the hypothesis calls for; don't expand or contract silently.
  - **Working-depth features.** Identify the **primary user journey** the hypothesis claims is better — the sequence of actions a user would take to actually get the value the hypothesis promises. Working-depth features are the bricks that make that journey complete inside the artifact. A feature in this list must produce **observable state change** for every action it claims: clicks mutate state, inputs persist, navigation lands somewhere real. **Cut breadth before you cut depth** — fewer screens with the journey actually executable beats more screens that just show what could exist. **Decorative buttons inside a working-depth feature are a contract violation.**
  - **Scaffolded features.** Which additional features appear in the IA for completeness but are visible-but-not-working? Scaffolds say what they are; they don't pretend to work. They communicate breadth so a viewer can imagine the full product without you needing to build it. Mock content is fine — even helpful — when it lets a viewer feel the shape of the product. **A scaffold never sits ON the primary user journey**; if a user has to traverse it to complete the journey, it belongs in working depth.
  - **File architecture.** Sketch the file layout before you write code: `index.html` (markup, entry), `styles.css`, `app.js`; additional `.html` files for multi-page surfaces. **Scaffold the files first** (empty shells are fine), then fill incrementally. The VFS is your work surface — Pi's `edit` tool is reliable on small, layered files and brittle on a single wall of inline code.
- **Honor the hypothesis's position on its exploration axes** (`dimensionValues`). The axis position decides which features dominate the IA and which sit quieter; encode it in chrome-vs-content weighting and disclosure choices.
- **Ground in `<specification>`.** Don't invent user needs, research findings, metrics, or business rules — pull only from what the spec provides.

</how_to_think>


<what_to_write>

Open with a structured `todo_write` before any code. The opening todo list must commit to the decisions made above:

- **Scope** — the scope you chose.
- **Working-depth features** — one todo per feature you commit to building.
- **Scaffold list** — one todo per feature you'll render as visible-but-not-working.
- **File architecture** — one todo per file you'll create (`index.html`, `styles.css`, `app.js`, additional pages). Scaffold these early in the build sequence.

Sequence the remaining build todos in whatever order makes sense to you and the coding agent.

</what_to_write>


<quality_bar>

Before you consider the run complete, reject outcomes that fail these checks:

- **Commitment incomplete:** the opening `todo_write` did not commit to scope, working-depth features, scaffold list, and file architecture.
- **Unrecognizable hypothesis:** a senior designer could not tell **which hypothesis** this artifact implements.
- **`measurements` unjudgeable:** the artifact is not expressive enough for a senior designer to score the hypothesis's design-critique criteria from inspection — typography choices, IA, copy tone, atmosphere are too generic or off-axis from what the measurements ask about.
- **Silent constraint breach:** the work contradicts non-negotiable constraints from the spec without acknowledging the tension in the UI.
- **Design-system drift (when a system was provided):** the output does not look or read like it belongs to the supplied design system without a justified reason tied to the hypothesis.
- **Journey not verified:** before writing `BUILD.md`, read your own code and locate the handler for every action you claimed as working depth. If a button has no handler, an input is never read, or a state change is described in copy but not in code — fix it or demote the feature to a scaffold. `BUILD.md` describes what the code does, not what you intended.
- **Wall of code:** substantial CSS or JS is inlined into `index.html`. Split into `styles.css` / `app.js` (scoped when shared).
- **Validation skipped:** finished without running `validate_html`, `validate_js`, and `validate_artifact` against the final files. Run them after each working-depth feature lands, and once more before `BUILD.md`. `validate_artifact` catches DOM ids referenced from JS that don't exist in the HTML — the dead-on-arrival handlers that ship as decorative bugs.

</quality_bar>


<final_report>

After all design files are written, write `BUILD.md` to the workspace root as your final action. Keep it short — not an essay.

- `## Scope` — one line: what you built (one screen / one flow / app).
- `## Working features` — each working-depth feature as `### Feature name`, then 1–2 sentences on the **user-observable behavior** (what state changes when they interact). If you can't describe a state change for a feature, it isn't working depth — move it to stubs.
- `## Stubbed features` — bullet list. Each line names the feature and what's missing (visuals only, no state, no backend, etc.).

If your final scope differs from your opening `todo_write` commitment, name the change in `## Scope`. This is the closing report — do not embed it inside any other artifact.

</final_report>
