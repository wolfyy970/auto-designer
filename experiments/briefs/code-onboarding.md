Software engineers joining a new team lose 2-4 weeks navigating an unfamiliar codebase before they can ship anything substantive. Existing onboarding materials — wikis, README files, architecture diagrams — go stale within a sprint and rarely answer the questions someone actually has at the moment they have them ("why is this function called from here?", "what's the actual entry point?", "is this code dead?", "who would I ask about this?").

The shape of the solution is open. It could be an IDE extension, a CLI, a browser-based codebase explorer, an AI pair-programmer that knows this specific repo, a Slack bot, a literate-programming layer over the existing code, a guided-tour generator — anything that helps a new engineer go from "just cloned the repo" to "shipped a non-trivial PR" faster. Don't constrain to the form factor of a destination web app; the right answer might not be a destination at all.

The user is a competent engineer (not a junior intern) who has technical chops but is unfamiliar with this specific codebase, this specific team's conventions, and where the bodies are buried. Time-to-first-meaningful-PR is the success metric; not training, not certification, not orientation videos.
