The user arrives on this flow in a hot state — locked out, often in the middle of something that has a clock on it. The design properties below are what an internal reviewer should be able to score by looking at the artifact, before any user research. They apply at the level of the reset flow itself plus whatever pre-auth and post-success surfaces it touches; they do not extend to the rest of the banking app.

State legibility at every step. At any screen, the user should be able to tell what just happened, what is happening now, and what they are expected to do next, in plain language sized to a stressed reader. That means error and status copy that names the actual situation ("we couldn't verify that code") instead of generic credential messaging, and a visible sense of where they are in the flow without burying them in progress chrome. Overpursuit: the screen turns into a status dashboard — multiple banners, persistent step indicators, redundant explanations stacked above the actual control — and the user can no longer find the one thing they came to do.

One primary action per screen, sized for someone who is not reading carefully. The design should leave no ambiguity about which control moves them forward at any given moment; secondary paths (try another method, get help, cancel) should be reachable but visually quieter. Overpursuit: the flow flattens into a chain of single-button screens that hide useful options the user actually wants — alternate verification methods, the ability to correct a typo without restarting — behind extra taps, lengthening the path under the banner of "simplicity."

A tone that acknowledges stress without performing empathy. Copy, pacing, and visual weight should read as calm and matter-of-fact — the design treating the user as someone solving a problem, not as a suspect being processed and not as a customer being soothed. (Inferred — the brief explicitly calls out the suspect-treatment failure mode and the stress state, which together imply a tone register the design has to hold.) Overpursuit: the interface becomes saccharine, padding every screen with reassurance copy and apology, which slows the user down and signals that something is wrong when nothing is.

A visible, in-flow escalation path when the automated reset cannot complete. The brief names "no clear escalation path when the automated reset fails" as a current failure; the design should make the handoff to human support reachable from inside the flow at the moment it becomes relevant, not buried in a separate help destination. The reviewer should be able to point to where, in the artifact, a stuck user gets unstuck. Overpursuit: escalation is offered too eagerly — a "talk to support" affordance on every screen, or a fallback presented before the automated path has actually failed — which both undermines the automated flow and pushes load onto support that the system could have handled.

Continuity across the verification sequence. The user enters this flow in motion; the design should preserve context across steps so that information already given is not asked for again, partial progress survives a reasonable interruption, and the path from "I started a reset" to "I am back in my account" reads as one continuous activity rather than a set of disconnected forms. Overpursuit: the flow caches and resumes so aggressively that a user on a shared or compromised device finds themselves mid-reset under someone else's session, or sensitive state lingers past where it should have been cleared.

A clean landing onto a post-success state that closes the loop. After a successful reset, the design should explicitly mark the task as done and put the user where they were trying to go — checking a balance, paying rent — rather than dropping them on a generic home surface and making them re-navigate. (Inferred — the brief frames the user's underlying goal as accessing the account for a specific purpose, and names post-success as in scope.) Overpursuit: the post-success surface becomes a marketing or upsell moment — security tips, product cross-sells, "while you're here" prompts — that delays the user from the thing they actually came to do.

Outcomes the design must avoid even when the properties above are satisfied:

- The user reaches a dead end with no next move — a final error screen, a "contact us" message with no contact, a state where the only option is to close the app and start over.
- The flow successfully completes but leaves the user uncertain whether it completed — ambiguous confirmation, no clear signal that the new password is now the one in effect, no indication of whether they are signed in.
- Security signaling overwhelms the task. Warnings, lockout countdowns, fraud-prevention language, and verification friction stack to the point where a legitimate user reasonably concludes they are being accused of something and abandons.
- The design solves the happy path elegantly but has no answer for the user whose phone number is wrong, whose recovery email is inaccessible, or whose device is new — populations who are disproportionately the ones actually using a reset flow.
